# 审批卡与自动跟随

只在审批卡出问题、或受控页被自动跟随改绑时读。常驻规则留在主文件：哪些调用要过审批卡、子代理不要直接调 `browser_*`、一次只有一个会话能操作浏览器。

## 一、审批卡：60 秒窗口，以及「为什么没看到提醒」

- **卡片在扩展自己的界面里，窗口固定 60 秒。** 超时有两种文案，含义相同，都是「卡
  弹过、没人应答、动作没执行」：导航类报
  `The browser approval request for "<工具名>" timed out before the user responded.`
  其余动作报 `The approval prompt for "<工具名>" expired before it was answered, so
  nothing ran.`（后者会直接告诉你下一步：让用户先看卡、再决定要不要重发）。这两句
  都是扩展产生的，**不等于宿主把审批关掉了**。
- **别把宿主那句 `Approval prompts are disabled in this session` 读成「本会话没有
  浏览器能力」。** 那句管的是沙箱提权（写文件、跳出沙箱的命令），和浏览器审批卡是两
  套东西。宿主侧同场景的报错文案是 `got no answer within Nms — the bridge's own
  budget`，两者按文案就能分开。看到带 `browser approval request for` 的那句，说明卡
  确实弹过、只是没人应答 —— 这种情况**重试永远无效**。
- **提醒有三种，每一种都可能不响。** ①助手窗口开着且不在前台时发系统通知；②没有任何
  助手页面时，尝试打开状态窗（浮动窗形态能打开，侧栏形态没有用户手势会被 Chrome 拒绝，
  于是只剩通知）；③宿主在调用静默 20 秒后会向用户提问「是不是有个确认卡在等」。
  通知开关在设置里（默认开），创建失败会记进扩展 debug log 的 `notification-failed`。
  窗口在前台时不发通知，所以「用户就坐在 Chrome 前面」也可能什么都没弹。
- **通知一条都不出现时，先查系统，不是查代码。** macOS 的通知设置里同一个 app 可能登记了
  两条（旧通知通道与 Chrome 152+ 的原生通道各一条），其中一条是「关闭」时，扩展的通知会
  被系统静默丢掉，而 `chrome.notifications.create` 照样成功、debug log 里也不会有失败。
  让用户把两条都设为允许通知。代码层能自证的只有一句：日志里没有 `notification-failed`。

**做完了，能指出这一条：**超时文案属于导航类还是其余动作类，以及通知没响时查的结果是「系统设置里两条通知通道」还是「debug log 里出现了 `notification-failed`」。

## 二、自动跟随：受控页被换掉时，回答会先说

用户在扩展设置里配了「自动跟随的站点」（`followOrigins`）时，这些站点上**新打开**的页面
会把本会话的受控页直接改绑过去（只限绑定之后新开的页，已开的页不动）。没配过的域名如果
是**在新窗口**里打开的，浏览器面板会弹一张确认卡（「跟随这次 / 不跟随 / 总是跟随此站点」），
用户选「总是」才写进列表；模型看不到这张卡，只会看到结果——跟了就出现下面那行提示。
典型场景是抓取类扩展：它在页面上取完数据，再在新窗口打开业务系统的录入表单，本会话就
跟着过去。

改绑后，模型的下一条**成功**工具回答开头会有一行：

`This session was moved to tab N — <url> — because that page opened on a follow origin. The previous page is no longer under this session's control: re-read this page before acting on it.`

判据与动作：

- 看到这行就以它为准：**旧页的快照、选择器、坐标全部作废**，先重新 `browser_snapshot`
  或 `browser_get_text` 读新页，再继续。不要拿旧页的上下文往新页上套。
- 这行只出现一次；它出现后旧页的会话授权已被撤销（页面换了），动作会重新问一遍。
- 没命中跟随列表的新页面不会自动跟；需要时仍用 `browser_bind_interactive` 让用户选。

**做完了，能指出这一条：**工具回答开头有没有 `This session was moved to tab N` 那行；有的话，重读后的新页 URL。

## 三、点击前先判断：新标签页是目标还是副作用

自动跟随只认站点白名单，不知道你的意图，所以判断要在**点击之前**做。判据是你手上的任务：
调研要打开的那篇资料、用例要走的下一步。登录框、分享框、广告、协议页归到副作用一类。

| 站点在白名单 | 这一击打开的新页面是 | 会发生什么 | 你该怎么做 |
|---|---|---|---|
| 是 | 目标页 | 点完会话自动跟过去 | 正常点，跟过去后重读页面 |
| 是 | 副作用 | 点完会话照样被带走 | 跳过这一击，继续在当前页做事；确实要点，先记下原页 URL，跟过去后用 `browser_bind_interactive` 切回来 |
| 否 | 目标页 | 浏览器面板弹卡问用户 | 正常点，等用户决定；用户选「总是」才写进白名单 |
| 否 | 副作用 | 不问也不跟，会话留在原页 | 正常点，忽略新开出来的那个窗口 |

跟过去之后发现它不是目标页：用 `browser_bind_interactive` 让用户选回原来那个标签页。
**原标签没被关掉就一直在选页列表里**，可以来回切；关掉了才是真的丢了。

**做完了，能指出这一条：**这次点击前判断的结果（目标页 / 副作用）、它有没有真的开出新标签页，以及跟过去之后原标签页还列在 `browser_bind_interactive` 里。
